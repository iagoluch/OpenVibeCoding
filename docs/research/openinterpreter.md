# OpenInterpreter — architecture and interface study for the OVC desktop app

Consulted on 2026-10-15, from public sources only (GitHub repositories, official docs site, open issue trackers). OpenInterpreter is **not installed** on this machine; no executable was obtained and no runtime artefact was inspected. Every claim below links to its primary source. Where a statement is an inference about UX rather than a documented fact, it is marked as such.

> **Read §0 first.** OpenInterpreter changed identity between 2024 and 2026. The common mental model — "Python interpreter with an AGPL license and an Electron desktop app in the repo" — describes the *legacy* product. The current mainline is a Rust project (a Codex fork, Apache-2.0) whose desktop app is a separate repository.

## 1. Architecture

### 1.1 Core vs interfaces (current mainline, "OIX")

Terminology used by the project: **OIX** = Open Interpreter, the runtime; **Workstation** = the desktop/browser app.

What the runtime repository ships ([README](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/README.md), [repo tree](https://api.github.com/repos/openinterpreter/openinterpreter/git/trees/main)):

| Surface | Form | Notes |
| --- | --- | --- |
| TUI | `interpreter` / `i` | Interactive terminal client; app-server-backed ([docs/app-server.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/app-server.md)) |
| Non-interactive | `interpreter exec` | NDJSON events with `--json`, `--output-schema`, `--verify` ([docs/exec.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/exec.md)) |
| Editor integration | `interpreter acp` | Agent Client Protocol over stdio, for ACP-compatible editors ([README](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/README.md), [docs/acp.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/acp.md)) |
| App platform protocol | `interpreter app-server --listen stdio://` or `ws://127.0.0.1:9000` | JSON-RPC server used by rich clients: "threads, streamed events, approvals, session state, model selection, and MCP status inside another application" ([docs/app-server.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/app-server.md)) |
| SDK compatibility | Codex SDK with a one-line binary override (`Codex({ codexPathOverride: "interpreter" })`) | Speaks "the same Codex exec protocol" ([README](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/README.md), [docs/sdk.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/sdk.md)) |
| MCP both ways | `interpreter mcp ...` (client) and `interpreter mcp-server` (server) | ([docs/cli-reference.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/cli-reference.md)) |
| Daemon | `interpreter app-server daemon start/stop/restart/version` | Optional shared runtime for multiple clients on localhost ([docs/daemon.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/daemon.md)) |
| Web demo | loopback-only Node bridge + browser page | Teaching example with explicit safety limits; explicitly "not for reproducing Workstation" ([docs/streaming-web-chat.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/streaming-web-chat.md)) |

The **desktop app is not part of the runtime repo**: "For a complete desktop, browser, or headless client, use [Interpreter Workstation](https://github.com/openinterpreter/interpreter-workstation)" ([README](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/README.md)). There is no Electron/Tauri code in the OIX tree.

### 1.2 How the app talks to the core (process + protocol, not embedding)

Interpreter Workstation's own architecture statement:

- "Open Interpreter owns the agent runtime, harnesses, provider/model discovery, and app-server protocol. This repository owns the shared Workstation shell, its desktop host, its browser host adapters, local policy, and workstation tools." ([workstation README](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/README.md))
- "Workstation is a client of the OIX app-server contract. Do not recreate OIX provider catalogs or harness logic in the Electron app." ([workstation AGENTS.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/AGENTS.md))
- The desktop app **installs and launches the exact checksummed OIX release pinned by the app**; the terminal and the app share one OIX home (`INTERPRETER_HOME`, default `~/.openinterpreter`) for configuration, sessions, plugins and skills ([workstation README](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/README.md)).

The wire contract is the **app-server JSON-RPC protocol, inherited from Codex app-server** ("Open Interpreter keeps that surface compatible so existing Codex app-server clients can use `interpreter app-server` as the launched process"; the full shape is documented upstream by OpenAI) ([docs/app-server.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/app-server.md)). Documented message flow, from the official browser example ([docs/streaming-web-chat.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/streaming-web-chat.md)):

1. Bridge spawns `interpreter app-server --listen stdio://` as a child process.
2. `initialize` → `initialized` (required order).
3. `thread/start` with `{cwd, sandbox: "read-only", approvalPolicy: "on-request"}` → thread id.
4. `turn/start` per prompt; stream `item/agentMessage/delta`; finish with `turn/completed` (status + error).
5. Server→client requests during a turn: `item/commandExecution/requestApproval`, `item/fileChange/requestApproval` — the example answers `{decision: "decline"}` and documents the rule "never accept one just because a browser is connected".
6. Client can cancel via `turn/interrupt`; responses are matched by JSON-RPC id, events by `threadId` + `turnId`.

Transport independence inside the app: one typed bridge (`src/ipc.ts`), three transports — Electron preload/IPC (desktop), HTTP under `/api` + SSE `/api/events` (browser against a local or remote sidecar), and an allowlisted snapshot/file relay for anonymous read-only publication ([docs/remote-workstation.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/docs/remote-workstation.md)).

Model-facing app tools use a CLI contract instead of a private tool bus: "Model-facing app tools use the `interpreter-app` command-line contract. The desktop app does not maintain a second provider or harness implementation" ([workstation README](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/README.md), [docs/interpreter.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/docs/interpreter.md)).

### 1.3 Session / state model

- Conversations are **threads owned by OIX**, persisted locally under `~/.openinterpreter/` (or `INTERPRETER_HOME`); resume/fork/compact are first-class commands (`interpreter resume --last|<id>`, `interpreter fork`, `/compact`) ([docs/sessions.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/sessions.md), [docs/daemon.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/daemon.md)).
- Workstation does not own history: "OIX owns the durable thread, current turn, native Goal, compaction, and rollout. Closing a tab or browser does not stop it. Workstation opens history on the newest page, paints only after it is positioned there, follows new output, and loads older pages when the user scrolls upward." ([docs/remote-workstation.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/docs/remote-workstation.md))
- **Goals**: a durable objective attached to a thread, created from the composer (`/goal <objective>`), with a compact card above the composer and statuses `active/paused/blocked/usageLimited/budgetLimited/complete`. Workstation is the control surface; OIX owns continuation, accounting and compaction ([docs/goals.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/docs/goals.md)).
- Exec sessions can be resumed too (`interpreter exec resume --last`), and history persistence is configurable (`[history] persistence = "none"`, `max_bytes`) ([docs/sessions.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/sessions.md)).

### 1.4 Code execution and consent

Two separate controls, exposed together via `/permissions` ([docs/sandbox.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/sandbox.md)):

- **Sandbox modes**: `read-only`, `workspace-write` (network off unless enabled), `danger-full-access`. Enforcement is OS-level (macOS Seatbelt; Linux/WSL Bubblewrap+seccomp; Windows native sandbox "where configured"), and the documented rule is to **fail closed** when a policy cannot be enforced.
- **Approval policies**: `untrusted` (ask before state changes), `on-request` (run in sandbox, ask before escalation), `never`. `--yolo`/`--dangerously-bypass-approvals-and-sandbox` remove both and are documented as VM/container-only.
- **Permission profiles** refine this per path/domain: `default_permissions = ":workspace"` or custom TOML with `workspace_roots`, filesystem rules (`read|write|deny`, deny wins, glob deny like `**/*.env`), network allow/deny domains, Unix socket allowlists ([docs/permissions.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/permissions.md)).
- In the app-server protocol, approvals are **round-trip requests inside the turn** (command and file-change variants), so the client UI is the consent surface ([docs/streaming-web-chat.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/streaming-web-chat.md)). Workstation has a dedicated `Approvals.tsx` component and per-agent file permissions ("File permissions are per agent. Every tool path must enforce the effective agent scope") ([workstation AGENTS.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/AGENTS.md), [components tree](https://api.github.com/repos/openinterpreter/interpreter-workstation/git/trees/5c35e3183fd1194c2be9faba530c80df42fbbdfa)).
- Read-only mode is an explicit **host** policy, not a UI guess: "Do not rely on disabled UI to protect mutations" — the backend rejects mutations with 403 while the UI removes the controls ([docs/remote-workstation.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/docs/remote-workstation.md)).

### 1.5 Separation vs coupling — summary

| Kept separate | Deliberately shared/coupled |
| --- | --- |
| Agent runtime (OIX) vs app shell (Workstation) — two repos, one-directional dependency | One OIX home directory (`~/.openinterpreter`): config, sessions, plugins, skills — so the TUI and the app see the same conversations ([workstation README](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/README.md)) |
| Desktop renderer vs transports: same React renderer for Electron, browser and read-only publication hosts | Protocol: app-server JSON-RPC inherited from Codex app-server; exec protocol kept Codex-SDK compatible |
| Business logic in `server/handlers`; Electron IPC and HTTP are "transports around that logic" | Portability mandate: `AGENTS.md`, `.agents/skills/`, MCP, ACP are read in place; `~/.openinterpreter` only for state with no shared standard ([docs/portability.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/portability.md)) |
| Distribution config vs application code: profiles inject endpoints/branding via `product.json` overlays; "A subscription may authorize operated services; it must not unlock a private client feature" | Trademark separation: "Codex" belongs to OpenAI and is not licensed ([docs/project-license.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/project-license.md)) |

### 1.6 Distribution and packaging

- **Runtime**: public install scripts — `curl -fsSL https://www.openinterpreter.com/install | sh` and, on Windows, `irm https://www.openinterpreter.com/install.ps1 | iex`; managed "standalone layout" with self-update (`interpreter update`, `check_for_update_on_startup`); uninstall instructions preserve user data; logs under `~/.openinterpreter/log/`. No pip path for the new runtime ([docs/install.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/install.md)). Release bundles are built with `scripts/build-interpreter-release.sh`, not ad hoc `cargo build`.
- **Desktop app**: Electron 42 + electron-builder 26 (macOS dmg/zip candidates, `electron-builder-squirrel-windows` for Windows, `electron-updater`), three shipped profiles — community (no hosted account, no telemetry), official (public hosted coordinates, signed/notarized releases with checksums, SPDX SBOM, GitHub attestations) and internal (same source, separate app id, unsigned review build). Build: `pnpm run build:official` / `package:official` ([docs/distributions.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/docs/distributions.md), [package.json](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/package.json)).
- **Legacy Python**: pip-installable from the community fork's git URL ([fork README](https://raw.githubusercontent.com/endolith/open-interpreter/main/README.md)).

## 2. Interface inventory

### 2.1 Desktop app — Interpreter Workstation

Self-description: "An open, neutral AI workspace for your computer… the open-source alternative to Claude Cowork and ChatGPT for work" (repo description; [README](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/README.md)). Young project: created 2026-08-01, ~24 stars, 16 open issues/PRs at consult time ([repo API](https://api.github.com/repos/openinterpreter/interpreter-workstation)).

**Stack (all public).** Electron 42.10 (main process `electron/main.ts` + `preload.ts` + `menu.ts` + `trayMenu.ts` + `autoUpdater.ts` + `crashReports.ts`), React 19.3 + Vite 8 + Tailwind 4 + shadcn-style tokens, Redux + `use-sync-external-store`, TipTap (rich-text editing), xterm.js + node-pty (embedded terminal), `react-window` + `@tanstack/react-virtual` (virtualized history), `use-stick-to-bottom` (chat scroll behavior), react-markdown/remark, `motion`, lucide-react, zod, `json-rpc-2.0`, MCP SDK, i18next/i18n; a **Bun/TypeScript sidecar** (`server/standalone.ts`, scripts `sidecar`/`headless`) hosts the app-side tools and HTTP API; document viewers via `@file-viewer/*` and pdfjs-dist; packaging via electron-builder/Squirrel ([package.json](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/package.json)). Repo requirements for source builds: Node 22, pnpm 9, Bun, Rust stable + Cargo, git submodules ([README](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/README.md)).

**Onboarding / first run** — there is a dedicated onboarding module tree with screens: `AiSetupScreen`, `ModelSetupScreen` (63 KB), `ModelPackReviewScreen` (56 KB), `ToolAddonsScreen` (62 KB), `WebToolsStep`, `ToolSetupStep`, `WorkspaceChoiceScreen`, `PrivacyScreen`, `NameScreen`, `FeatureCardSlide`, `VisionScreen`, `StayConnectedScreen`, `ExtensionDownloadBar`, `FeedbackScreen`, plus overlay-specific first-use and permissions screens (`OverlayFirstUseScreen`, `OverlayPermissionsScreen`) and Simple-mode variants (`SimpleWorkspaceChoiceScreen`, `SimpleBrowserSetupScreen`, `SimpleWhatsAppSetupScreen`, `SimpleMcpSetupScreen`). **Simple mode (explicitly beginner-oriented).** A separate shell (`SimpleShell.tsx` 53 KB, `SimpleInterface.tsx`) where the agent **generates the app's interface itself**: "Simple mode is a live, filesystem-backed React application hosted by Workstation… Generated code is compiled by app-shipped esbuild in Electron's main process. Users do not need Node, Bun, Vite, or a package install." Maintained capability modules (`@interpreter/interface`, `@interpreter/motion`), durable state in `.interpreter/state.json`, host-provided file/folder viewers, host-restorable UI state ([docs/simple-interface-runtime.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/docs/simple-interface-runtime.md)). Simple and Advanced are "two experiences in the same Workstation application" ([docs/simple-mode-roadmap.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/docs/simple-mode-roadmap.md)). **However, at consult time two open PRs ("Make Simple the default desktop experience", #153/#155) indicate the default experience is still the advanced shell** ([issues list](https://api.github.com/repos/openinterpreter/interpreter-workstation/issues?state=open)).

**What is genuinely beginner-friendly (documented):** first-run provider walkthrough in the TUI ("sign in with ChatGPT, use an API key, connect Ollama or LM Studio, or configure another compatible provider", [docs/quickstart.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/quickstart.md)); a GUI onboarding wizard that sets up model, tools and workspace in screens instead of flags; plain-language approvals; account-optional community build; read-only inspectors; the Simple shell hiding the file/tab machinery.

**Known weaknesses (docs and open issues):**

- Desktop app with local models: "[Bug]: Desktop app ignores function-calling disablement and loops raw JSON with Ollama" — the reporter shows the same model works in the CLI with `--no-llm_supports_functions` ([issue #1938](https://github.com/openinterpreter/openinterpreter/issues/1938)).
- Windows: "HttpClientHandler TypeNotFound breaks all desktop CUA tools in Interpreter" ([workstation issue #182](https://github.com/openinterpreter/interpreter-workstation/issues?state=open)).
- Verification trust: "[Bug] Completion or a verification result is reported without the work or check being performed" — the agent claimed completion/identical-file checks without tool calls; the docs themselves warn that "a zero exit status… does not prove that an arbitrary instruction's intended side effect happened" and offer `--verify` ([issue #1926](https://github.com/openinterpreter/openinterpreter/issues/1926), [docs/exec.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/exec.md)).
- Complexity: running from source needs Node+Bun+Rust+submodules; the browser/web renderer, publication API, overlay and messaging channels make the surface large; the app is young (created 2026-08-01) with ~24 stars.
- Beginner default not yet claimed: "Make Simple the default desktop experience" is still an open PR.

### 2.2 CLI — main flows and interaction patterns

Entry: `interpreter` (alias `i`); first run walks provider setup; `interpreter "prompt"` starts with a prompt; `interpreter -i screenshot.png "…"` attaches images. ([docs/quickstart.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/quickstart.md), [docs/interactive.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/interactive.md))

Composer and keys: `Enter` send, `Shift+Enter` newline, `/` slash commands, `@` fuzzy file mentions, `Ctrl+G` edit in `$EDITOR`, `Ctrl+R` prompt history search, `Tab` queue a follow-up while running, `Esc` back out, `Ctrl+C` twice to quit. ([docs/interactive.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/interactive.md))

Workflow commands: `/plan` (inspect and propose before editing), `/review` (code-review pass over current changes), `/new`, `/resume`, `/fork`, `/compact`, `/clear`, `/copy`, `/theme`, `/status`, `/model`, `/permissions`, `/harness`, `/goal`; background terminals via `/ps` and `/stop`. Approvals appear inline before a command runs; "the default posture is designed for day-to-day work in a trusted repository: workspace access is allowed, and actions outside the active policy ask first." ([docs/interactive.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/interactive.md), [docs/goals.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/docs/goals.md))

Harness switching is a headline CLI feature: `/harness` selects `native`, `claude-code`, `claude-code-bare`, `zcode`, `kimi-code`, `kimi-cli`, `qwen-code`, `deepseek-tui`, `swe-agent`, `minimal` — emulating the harness each low-cost model performs best under ([README](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/README.md), [docs/harness.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/harness.md)).

Automation patterns: `interpreter exec …` with `--json` NDJSON events, stdin prompts (`cat task.md | interpreter exec -`), `--output-schema`, `--output-last-message`, and a documented CI YAML pattern with `OPENAI_API_KEY` and `--sandbox read-only` ([docs/exec.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/exec.md)). Remote TUI: `interpreter --remote ws://127.0.0.1:9000` and `wss://… --remote-auth-token-env VAR` with a "do not expose an unauthenticated listener" warning ([docs/app-server.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/app-server.md)).

### 2.3 The legacy desktop era (context only)

- The classic Python project's README linked an external "Desktop App" (OS Mode era) and provided `interpreter --profile os` for provider-agnostic desktop control ([fork README](https://raw.githubusercontent.com/endolith/open-interpreter/main/README.md)).
- The `01` project (voice interface; AGPL-3.0; ~5.2k stars) advertises a "Desktop Client" alongside Android/iOS and ESP32 clients, but its last push was **2024-11-01** — it is dormant ([01 README](https://raw.githubusercontent.com/openinterpreter/01/main/README.md), [01 repo API](https://api.github.com/repos/OpenInterpreter/01)). No public desktop-app implementation for that era survives as an actively maintained artifact inside these repositories, so it is not a usable architecture reference.
- Classic interaction safety default: "By default, you'll be asked to approve code before it's run"; `-y`/`%auto_run` bypass it; interactive commands (`%verbose`, `%reset`, `%undo`, `%save_message`, `%jupyter`, `%markdown`) and a `pip` install path ([fork README](https://raw.githubusercontent.com/endolith/open-interpreter/main/README.md)).

## 4. The five most decisive facts for OVC's desktop app

1. **Runtime and shell are separate processes joined by a versioned protocol — and the app pins the runtime.** Workstation spawns a checksummed OIX binary and speaks app-server JSON-RPC (`initialize`/`thread/start`/`turn/start`/`item/agentMessage/delta`/`turn/completed`/approval requests). OVC already has a daemon with authenticated loopback IPC; the decisive move is to expose a documented, versioned app-server-style protocol as the *public* contract between `ovc` and the future desktop client, so the TUI and the GUI stay thin clients of one runtime, instead of the desktop app embedding the agent loop. ([docs/app-server.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/app-server.md), [docs/streaming-web-chat.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/streaming-web-chat.md), [workstation README](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/README.md))
2. **One shared home makes the terminal and the GUI the same product.** Both surfaces read the same `~/.openinterpreter` home, so a session started in the TUI can be opened in the app and vice versa; the app only adds shell state (tabs) on top of runtime-owned threads, and history is paged oldest-on-demand while the runtime stays the durable record. For OVC this argues for SQLite-session continuity across CLI and GUI as the visible selling point, plus "resume/fork/compact" UI. ([workstation README](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/README.md), [docs/remote-workstation.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/docs/remote-workstation.md))
3. **Beginner UX is treated as a distinct shell, and it is the part that is still unfinished.** Workstation invests heavily in onboarding (dedicated wizard screens for AI/provider, tools, workspace, privacy, plus overlay permission screens) and in "Simple" mode with its own shell and settings — yet the PR to make Simple the *default* is still open, and the advanced shell exposes profiles, MCP, terminal, browser extension, messaging channels. The actionable lesson for OVC: a friendly first-run wizard plus a reduced beginner shell is a differentiator worth designing as the default experience, not a skin over the power-user UI. ([onboarding tree](https://api.github.com/repos/openinterpreter/interpreter-workstation/git/trees/7b1459d20de79c40849fc79dc7e4785be22afe13), [docs/simple-interface-runtime.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/docs/simple-interface-runtime.md), [issues list](https://api.github.com/repos/openinterpreter/interpreter-workstation/issues?state=open))
4. **Consent is a protocol-level, per-turn round-trip with explicit policy names, and read-only is a host policy.** Approvals arrive as `item/commandExecution/requestApproval` / `item/fileChange/requestApproval` during a turn; sandbox modes and approval policies are separate knobs; the browser demo is required to *decline by default*; and read-only hosts reject mutations server-side with the UI merely reflecting that. OVC's approvals (currently streamed to the owning client) should be documented with the same clarity: named policies, per-agent scoping, fail-closed behavior, and a UI that shows exactly what is being approved (command, files, scope). ([docs/sandbox.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/sandbox.md), [docs/permissions.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/permissions.md), [docs/streaming-web-chat.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/streaming-web-chat.md), [workstation AGENTS.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/AGENTS.md))
5. **"Agent said done" is not "done" — the interface exists to show evidence.** The project's own docs warn that a completed turn does not prove the intended side effect occurred, and there is an open bug report of completion/verification claims made without any tool call. Workstation's answer is rich, retrievable evidence in the shell: virtualized full history, file tabs synced to the agent's context, diffs, document viewers and a Goal card with explicit terminal statuses. For a beginner-facing OVC app, surfacing tool traces, diffs and verification evidence (and labelling "reported" vs "verified") is arguably *more* valuable than prettier chat bubbles. ([docs/exec.md](https://raw.githubusercontent.com/openinterpreter/openinterpreter/main/docs/exec.md), [issue #1926](https://github.com/openinterpreter/openinterpreter/issues/1926), [docs/goals.md](https://raw.githubusercontent.com/openinterpreter/interpreter-workstation/main/docs/goals.md))
