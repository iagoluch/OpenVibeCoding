# Security and execution guarantees

## Workspace file tools

`os.Root` provides traversal-resistant file access. Absolute/parent paths and symlink components are rejected. Secret locations (`.env*`, `.ssh`, `.aws`, credential filenames and private-key extensions), generated directories and `.gitignore` matches are excluded from ordinary read/search/list tools. Reads accept regular UTF-8 text up to 128 KiB. This is a denylist and ignore policy, not a general secret detector. Nested ignore handling is deliberately conservative: an ancestor exclusion cannot be reopened by a nested exception.

A proposal does not write. Each replacement/deletion shows a unified diff; each move names its source/destination and shows the affected content. Approval applies to one operation. The original file digest is rechecked before mutation. Replacements use exclusive temporary files, fsync and rename; moves create the destination exclusively before removing the original. If a move cannot remove its source, it reports the partial result rather than claiming success. Parent directories may be created inside the root. Unrelated destination files are never overwritten by a move.

The boundary protects against model-supplied paths, not a hostile concurrent local process, hard links or mounted filesystems controlled by the same OS user. Digest checking and replacement are not a filesystem-wide compare-and-swap; avoid concurrent external edits during application. Per-workspace runtime exclusion prevents two agent turns from modifying the same workspace concurrently.

## Linux process isolation

Default shell execution uses Bubblewrap and fails closed if unavailable or denied by host policy. The sandbox exposes `/usr` and required system runtime directories read-only, an ephemeral `/tmp`, limited devices, and the selected project at `/workspace`. Host home and `/proc` are absent. Protected secret entries inside the project are masked; dependency directories remain available so builds can use installed dependencies. It requests separate namespaces, a new session and parent-death termination. It is not claimed to mitigate kernel vulnerabilities or side channels.

Network is isolated by default. An explicit network grant shares the host network and mounts required resolver/certificate files; the approval labels network-enabled execution. An explicit install grant allows the package-install tool. General shell code can perform equivalent operations inside its allowed filesystem/network boundary, so tool-category grants alone are not semantic enforcement of arbitrary programs.

There is currently no built-in process sandbox on macOS or Windows. Confined command requests fail closed there. `--allow-unsandboxed-shell` deliberately opts into host-user execution on any platform, with per-command approval and an explicit warning in the review. It can access host paths, network and installed applications. Never enable host mode when a stronger OS boundary is required. OS privileges are never escalated automatically.

Children receive a small environment allowlist instead of provider credentials. Host mode can nevertheless read credentials from host files. Commands have a sixty-second limit and bounded stdout/stderr. Unix host-shell cancellation kills its process group; automation workers also use process groups. Windows uses process-tree taskkill on cancellation. Intentionally detached processes and completed actions are not guaranteed reversible or terminable. These are cancellation mechanisms, not OS isolation on Windows/macOS.

## Runtime

A random 256-bit token authenticates loopback IPC. The token file is private, is never displayed, and clients reject non-loopback addresses/redirects. Requests are bounded, methods/routes validated, and cross-origin browser requests rejected. OS locks prevent duplicate daemons and release automatically after crashes. Metadata is replaced only after acquiring ownership. Protocol mismatches fail rather than silently using incompatible state.

Approval IDs are random, one-use and bound to the originating client identity. Storage mutation belongs to the runtime; direct client append/summary/usage writes are rejected. Active sessions cannot be deleted, recovered, renamed or exported. Turns are serialized by session and workspace. A disconnected client cancels its own request; unrelated clients continue. Runtime stop refuses active tasks; OS termination cancels them before storage shutdown.

The local authenticated user can configure grants and endpoints. Authentication does not make an AI-generated command trustworthy: every mutation, shell command and automation action still goes through approval, and inspect mode refuses them.

## Browser UI (loopback web client)

`ovc --ui` starts the shared runtime and prints one pairing link. The code in it is 256-bit random, single use and expires after five minutes; only a client holding the bearer token may mint one, and the code is never written to the runtime log. Opening the link exchanges the code for the `ovc_ui` cookie and redirects to `/`. The cookie is HttpOnly, SameSite=Strict, host-only with `Path=/`, and has no `Secure` attribute because the transport is loopback HTTP. Every request is authenticated on its own: the cookie is compared to the runtime token in constant time, so the code governs the exchange, not later requests. The API answers a browser GET with 405. Page and assets carry `default-src 'self'` with no inline or remote code, `frame-ancestors 'none'`, `form-action 'none'`, `base-uri 'none'`, plus `nosniff`, `no-referrer` and `no-cache`. Every response carries `nosniff` and `no-referrer`; the API, the streaming turn and the pairing answer carry `no-store`, so only the page and its assets may be revalidated. No CORS header is ever served, so a foreign page cannot read a response and its preflight fails on 405. Assets come only from the embedded tree: `/assets/` paths pass `fs.ValidPath` and never touch the filesystem.

A browser request must additionally arrive on the origin the daemon owns. `Host` must equal the exact loopback address; `Origin`, when present, must be that same origin; `Sec-Fetch-Site`, when present, must be `same-origin` or `none`. Non-browser clients send neither and are authenticated by the bearer token alone. A DNS name that rebinds to `127.0.0.1` still arrives with its own `Host` and is refused before authentication; a foreign page's navigation or fetch is refused by origin and fetch metadata. The listener binds `127.0.0.1` only: there is no LAN or remote surface.

The cookie value *is* the runtime token, and that is a conscious trade-off: one secret to store and audit, no second credential lifecycle, no rotation service. The consequence is stated plainly: whoever obtains the cookie holds the token's full authority — session deletion and export, provider and credential changes, `/run` turns including host-shell and permission overrides, and runtime stop. The offsetting controls are that the value is minted by the daemon and never accepted from a request, that pairing cannot be fixed or pre-seeded, and that the cookie never reaches JavaScript or another origin. Removing the cookie is not revocation: the token lives until the runtime restarts, and re-pairing hands out the same one. A web page served from another port of `127.0.0.1` can try to overwrite or shadow the cookie (cookies are host-scoped, not port-scoped), but the runtime accepts any presented value that matches, so the paired tab keeps working; the page still cannot read the value. Treat the printed link as a short-lived secret — terminal scrollback, the browser launcher's command line and browser history are all places it can be copied from inside its five-minute window.

Not protected, explicitly: any process running as the same OS user. It can read `runtime.json`, unlock the credential store, or talk to the loopback port directly, so the pairing flow, the cookie and the origin rules defend against web-page-originated confusion (CSRF, DNS rebinding, cross-origin reads) and against other machine users — not against the user's own programs, browser extensions, or a compromised browser. The pairing code protects the handoff, not the machine.

## Desktop shell (Wails window)

`ovc --desktop` (built with `-tags desktop`) opens a native window that renders the same web UI through a reverse proxy inside the Wails v3 asset handler. The shell is a third thin client of the runtime: no second agent loop, and the daemon code is unchanged.

The proxy is the trust position. The bearer token lives only in the shell process and is attached to each outbound request after the page's own `Authorization` and `X-OpenVibeCoding-Client` values are deleted — override, never append — together with the shell's per-window client id (`ovc-desktop-<random>`). Inbound `Cookie` and outbound `Set-Cookie` are stripped in both directions, so no token material ever reaches the webview or its cookie jar, and the same user-facing protection as pairing applies without a pairing step.

The proxy is default-deny. The page may read `/` and `/assets/*` and POST to `/health`, `/run`, `/approve`, `/store` and `/ui/*`; every other path is a proxy 404. `/pair` is blocked on both methods on purpose: the proxy injects the bearer credential, so proxying `/pair` would let a compromised page mint a pairing code and materialize a cookie with the token's full authority outside the proxy — token laundering. `/stop` is blocked too: stopping the service is a tray action, and the tray talks to the daemon directly with its own client identity. The runtime's own 2 MiB request cap is mirrored at the proxy so oversized requests are refused before the daemon. POST bodies are buffered and their `Content-Length` repaired before forwarding: wails v3 beta.30 on Windows delivers POST bodies with a zero `Content-Length` while the bytes are intact (to be reported upstream; the buffering leaves the bytes untouched).

The proxy origin is only reachable from inside the webview: the `wails.localhost` name resolves nowhere else — verified 2026-10-16, an external `Invoke-WebRequest` cannot connect. The origin rules are still enforced as defense-in-depth: inbound `Host` must be the asset origin, `Sec-Fetch-Site: cross-site|same-site` is refused (the value is forwarded untouched otherwise, and the daemon already accepts only same-origin/none), `CONNECT` and absolute-form targets are refused, and no CORS header is ever emitted. The daemon CSP reaches the webview unchanged; the only additions to the page are two same-origin module tags injected before `</head>`: the wails runtime (`/wails/runtime.js`, needed because wails v3 does not auto-inject it and the CSP forbids inline scripts) and the shell-owned `/ovc-bridge.js`. The wails v3 beta.30 runtime is a pure ES module that never assigns `window.wails`, so the alias imports its exported `Call` interface from the same-origin runtime URL, installs it on `window.wails` (a merge — anything already on `window.wails` or its `Call` is kept, never clobbered) and then maps the page's pinned binding name `desktop.UI.PickFolder` to the name wails actually registers (the full Go package path). The alias cannot create capability: `Call` only reaches methods the Go side already bound, exactly one name is rewritten, every other name passes through, and a failed runtime import leaves `window.wails` unset so the page keeps its plain-browser posture.

The bridge is confined to one method. `desktop.UI.PickFolder` opens the native folder chooser — mutex-serialized, one modal at a time, no path cache — and returns the chosen path (empty on cancel) or the dialog's error to the page; it never swallows failures. The path is only a proposal: the page sends it to the daemon, which validates it server-side like any workspace. Nothing else is bound — no file read or write, execution, environment, credential or keychain access, clipboard, network fetch, or arbitrary script surface — and a test enumerates the bound methods and fails if anything beyond `PickFolder` is registered.

Webview hygiene: the user-data folder lives under `%LOCALAPPDATA%\openvibecoding\webview-<random>`, never in roaming `%APPDATA%` or the install directory, and is unique per process — two processes sharing one folder deadlock the webview (POC-verified). It is removed best-effort at normal exit. At boot the shell also sweeps stale `webview-*` folders orphaned by shells that died before their exit cleanup: only folders older than one hour are considered, the current one is never touched, and a folder whose rename fails is skipped — Windows refuses the rename while any live process still holds a handle inside, typically another shell's webview, so "unsure" means "skip"; what was swept is logged. The webview is never given `--remote-debugging-port` or any other debugging switch (pinned by test).

The pre-existing `/run` posture is accepted for M1: a turn carries provider, model, harness, permissions and automation fields supplied by the client. A local caller can already talk to the daemon directly, so a cheap gate at the proxy would be theater; client identities remain assertable and the real fix — configuration opt-in — is scheduled for M2. M2 backlog, tracked (security F2): popup and new-window navigation interception in the desktop webview — the M1 window is a single top-level document and the proxy allowlist already narrows what a navigation can reach, but an explicit popup/new-window policy is follow-up work. The shell itself never stops the daemon: closing the window or quitting from the tray leaves the runtime running, matching `ovc --ui`; only the tray's "Parar serviço" asks the daemon to stop, and a busy daemon answers 409, keeps the turn alive and is never force-killed.

Supply-chain posture: all desktop code is behind the `desktop` build tag, and plain builds keep a wails-free dependency graph — asserted in CI with `go list -deps ./cmd/ovc`. The pinned stack is wails `v3.0.0-beta.30` plus four linked transitive dependencies (`github.com/adrg/xdg`, `github.com/coder/websocket`, `github.com/go-ole/go-ole`, `github.com/mattn/go-colorable`). The tagged graph additionally pulls `golang.org/x/exp`: wails requires `v0.0.0-20260410095643`, so minimal-version selection forces the bump from lipgloss's `20231006` to `20260410`, and the requirement reaches the plain binary's module graph too (via `charm.land/bubbletea/v2` → `charmbracelet/colorprofile` → `xo/terminfo`). Three more modules exist as go.sum-only entries that never reach a shipped binary: `github.com/go-json-experiment/json` (wails benchmark/test-only, not linked), `github.com/matryer/is` and `github.com/google/go-cmp` (wails test-only) — verified with `go mod why -m`. The Windows exe icon is embedded at build time with go-winres (`rsrc_windows_amd64.syso`); no installer toolchain is assumed — NSIS is not available on the machines that package releases, so M1 ships a portable exe. Workflow actions added for the desktop CI job are pinned by commit SHA; the release workflow follows its pre-existing `@v4`/`@v5` style.

Toolchain and vulnerability record (2026-10-19): the QA gate's `govulncheck` run reported 10 stdlib vulnerabilities affecting the untagged binary and 11 affecting the tagged desktop build (the GO-2026-6603..6617 class: net/http, HTTP/2, crypto/tls and related stdlib packages), all fixed in Go 1.27.2. Release binaries must therefore be built with Go ≥ 1.27.2. CI pins the toolchain accordingly: every job — the three-OS test matrix, packages, desktop and release — reads `go-version-file: go.mod` through `actions/setup-go` (v5; the desktop CI job pins v5.6.0 by commit SHA), and the module's `go` directive is 1.27.2, so no CI or release build can resolve an older toolchain; dev machines auto-switch to it (GOTOOLCHAIN=auto). Re-running `govulncheck` against the bumped module reports no vulnerabilities in either the untagged or the `-tags desktop` graph (verified 2026-10-19).

## Secrets, audit and context

Credentials come from environment overrides, OS keychain or explicitly selected file fallback. Unix fallback files with group/other access are refused. New files use 0600 and directories 0700; Windows relies on profile ACLs. No secret is included in JSON configuration. Known credential values and terminal controls are redacted before display/persistence. Arbitrary application secrets cannot be reliably detected: do not ask tools to print them. Sessions are not encrypted at rest.

SQLite records proposals/approvals before execution. Persistence failure stops the operation. Task starts/finishes and configuration changes are audited. A crash between mutation and durable result produces an unknown-outcome recovery message; it never causes automatic replay. Runtime logs contain operational metadata, not request bodies or screenshot data.

Original history is authoritative. Structured summaries retain source IDs and are not permissions. Recall retrieves originals in bounded chunks. Screenshots are transient: only a placeholder is stored, and image data is sent to the configured model during the current task. Users must authorize capture, choose an image-capable model and consider the information visible on screen.

## Browser and native desktop

Both are separately enabled and approved. Clipboard has an additional grant. The Playwright worker uses a fresh profile and an exact-origin page routing policy, blocks downloads/service workers/WebSockets, limits steps/time/output and reports actual failures. Its routing is not OS-level network isolation.

Native input acts on the user's visible desktop. Launch/focus is allowlisted; global mouse/keyboard gestures are not confined to one process. The user reviews the target/action before execution. Accessibility, Screen Recording, locked/UAC desktops and compositor restrictions are respected. Linux Wayland is unsupported by the built-in X11 backend. External adapters are trusted user configuration and must enforce their own OS policy. See automation.md for the action protocol and cancellation limits.
