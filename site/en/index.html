A coding agent
that shows its work.

OpenVibeCoding is a terminal coding agent that keeps the loop visible. It reads the project, proposes a diff, waits for your approval, then shows the command and the result. Sessions and evidence are stored on your machine.

A change is not done when the model says so.

It is done when the diff is reviewed and the command has an exit code. That is the loop OpenVibeCoding is built around.

01

Inspect

Reads project instructions, searches code and inspects Git state. Reads stay inside the workspace and do not ask for approval.

workspace · read-only

work/parser AGENTS.mdinstructions internal/parser/source + tests git statusclean
02

Review

Every write, move or delete arrives as a unified diff. A stale proposal is rejected when the file changes underneath it.

src/parser.go

-return nil +return validate(input)

stale proposals rejected

03

Approve

Ctrl+Y accepts one operation. Ctrl+N rejects it. Approval is per operation, never inherited from an earlier turn.

Ctrl+Yapprove this operation
Ctrl+Nreject this operation

one operation at a time

04

Verify

Approved commands return stdout, stderr and exit status. /changes shows what changed; /undo reverses the last applied change.

$ go test ./internal/parser

okinternal/parser0.012s

exit 0

Small surface. Explicit boundaries.

Each capability has a place to be granted, approved or refused. The terminal stays the interface; the runtime owns the limits.

The model proposes.
The runtime enforces.

A previous approval never authorizes new work. Every write, command and integration crosses its own boundary.

Capabilities and their enforced boundaries
File changes Unified diff before the operation, per-operation approval, and /undo for the last applied change.
Commands Approval first, then stdout, stderr and exit status. On Linux they run in Bubblewrap with no network by default; if isolation cannot be enforced, execution fails closed. Elsewhere, --allow-unsandboxed-shell is an explicit opt-in, not an OS sandbox.
Providers Native OpenAI, Anthropic and Gemini. Compatible DeepSeek, Kimi, Qwen, Mistral and local endpoints. Free-tier presets for OpenRouter, Groq, Cerebras, NVIDIA NIM, Z.AI and Google AI Studio.
Sessions SQLite history, summaries, audit records and usage. Resume a saved session after a restart.
Beyond the terminal Playwright browser QA and platform desktop tools, behind separate browser, desktop and clipboard grants. The built-in desktop backend does not support Wayland.

The same loop, at your pace.

Set up for a first project, a daily workspace, or a host where isolation is not optional.

First project

Start with a local model or a free-tier preset. The setup wizard tests one real request before activating a provider. File changes still wait for a diff.

ovc --setup detects Ollama and LM Studio, lists free-tier key pages, and stores credentials in the OS keychain by default.

Daily work

Sessions survive restarts, older exchanges are summarized, and /undo reverses the last applied change. Use browser QA when the task leaves the code, or ovc --ui when a browser is the better surface.

Original history stays in SQLite. An undo is refused if the file changed after the operation, so newer work is never overwritten silently.

Strict environments

Use a native adapter or your own compatible endpoint. On Linux, approved commands run in Bubblewrap with no network by default; when isolation cannot be enforced, execution fails closed. Network and install grants start off.

--allow-unsandboxed-shell runs approved commands with your user privileges. It is an explicit choice, not isolation.

Pre-1.0: interfaces and provider support can change between releases.

From clone to first session.

Release binaries do not need Go: the install script downloads the archive for your OS and CPU and verifies its SHA-256. Source builds need Go 1.26.2+.

Clone the public repository, run the installer for one release archive, then choose a provider and open a workspace.

  1. Get the code

    Clone the repository; the installer and the source live there.

  2. Install the binary

    The script downloads and verifies the archive for your OS and CPU, then installs ovc to ~/.local/bin (or %LOCALAPPDATA%\Programs\OpenVibeCoding on Windows). Add that directory to PATH if ovc is not found.

  3. Choose a model

    ovc --setup offers local servers and free-tier presets, then tests one real request.

  4. Open a project

    Point ovc at a workspace. Reads are immediate; writes and commands wait for approval.

git clone https://github.com/iagoluch/OpenVibeCoding.git
cd OpenVibeCoding
bash scripts/install.sh
# if ovc is not found, add ~/.local/bin to PATH
ovc --setup
ovc --workspace /path/to/project

Status

OpenVibeCoding is under active development. Native macOS and Windows runtime behavior still requires validation on those hosts; Linux browser, desktop and sandbox workflows have been tested. Cross-compilation does not certify native runtime behavior. See the latest release or the full guide.
