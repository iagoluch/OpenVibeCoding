Um agente de código
que mostra o que faz.

O OpenVibeCoding é um agente de programação de terminal que mantém o ciclo visível. Ele lê o projeto, propõe um diff, espera sua aprovação e então mostra o comando e o resultado. Sessões e evidências são armazenadas na sua máquina.

Go + Bubble Tea·Sessões SQLite·MIT

Uma mudança não termina quando o modelo diz que terminou.

Ela termina quando o diff é revisado e o comando tem um código de saída. É em torno desse ciclo que o OpenVibeCoding é construído.

01

Inspecionar

Lê as instruções do projeto, pesquisa o código e inspeciona o estado do Git. Leituras ficam dentro do workspace e não pedem aprovação.

workspace · somente leitura

work/parser AGENTS.mdinstruções internal/parser/código + testes git statusclean
02

Revisar

Toda escrita, movimentação ou exclusão chega como um diff unificado. Uma proposta obsoleta é rejeitada quando o arquivo é alterado depois da proposta.

src/parser.go

-return nil +return validate(input)

propostas obsoletas rejeitadas

03

Aprovar

Ctrl+Y aceita uma operação. Ctrl+N a rejeita. A aprovação é por operação, nunca herdada de um turno anterior.

Ctrl+Yaprovar esta operação
Ctrl+Nrejeitar esta operação

uma operação por vez

04

Verificar

Comandos aprovados retornam stdout, stderr e código de saída. /changes mostra o que mudou; /undo reverte a última alteração aplicada.

$ go test ./internal/parser

okinternal/parser0.012s

exit 0

Superfície pequena. Limites explícitos.

Cada capacidade tem um lugar para ser concedida, aprovada ou recusada. O terminal continua sendo a interface; o runtime controla os limites.

O modelo propõe.
O runtime impõe.

Uma aprovação anterior nunca autoriza trabalho novo. Cada escrita, comando e integração atravessa sua própria fronteira.

Capacidades e suas fronteiras aplicadas
Alterações em arquivos Diff unificado antes da operação, aprovação por operação e /undo para a última alteração aplicada.
Comandos Aprovação primeiro; depois stdout, stderr e código de saída. No Linux, rodam em Bubblewrap sem rede por padrão; se o isolamento não puder ser aplicado, a execução falha fechada (fail closed). Em outras plataformas, --allow-unsandboxed-shell é uma escolha explícita, não um sandbox de SO.
Provedores OpenAI, Anthropic e Gemini nativos. DeepSeek, Kimi, Qwen, Mistral e endpoints locais compatíveis. Presets de planos gratuitos para OpenRouter, Groq, Cerebras, NVIDIA NIM, Z.AI e Google AI Studio.
Sessões Histórico, resumos, registros de auditoria e dados de uso, guardados em SQLite. Retome uma sessão salva após reiniciar.
Além do terminal QA de navegador com Playwright e ferramentas de desktop da plataforma, sob permissões separadas de navegador, desktop e área de transferência. O backend de desktop embutido não suporta Wayland.

O mesmo ciclo, no seu ritmo.

Configurado para um primeiro projeto, um workspace diário ou um host onde isolamento não é opcional.

Primeiro projeto

Comece com um modelo local ou um preset de plano gratuito. O assistente de configuração testa uma requisição real antes de ativar um provedor. Alterações em arquivos ainda esperam um diff.

ovc --setup detecta Ollama e LM Studio, lista as páginas de emissão de chaves dos planos gratuitos e armazena credenciais no keychain do sistema por padrão.

Trabalho diário

Sessões sobrevivem a reinícios, interações mais antigas são resumidas e /undo reverte a última alteração aplicada. Use QA de navegador quando a tarefa ultrapassar o código, ou ovc --ui quando o navegador for a superfície melhor.

O histórico original fica no SQLite. Um undo é recusado se o arquivo mudou depois da operação, para que trabalho mais novo nunca seja sobrescrito em silêncio.

Ambientes restritos

Use um adaptador nativo ou seu próprio endpoint compatível. No Linux, comandos aprovados rodam em Bubblewrap sem rede por padrão; quando o isolamento não puder ser aplicado, a execução falha fechada. Permissões de rede e instalação começam desligadas.

--allow-unsandboxed-shell roda comandos aprovados com os privilégios do seu usuário. É uma escolha explícita, não isolamento.

Pré-1.0: interfaces e suporte a provedores podem mudar entre releases.

Do clone à primeira sessão.

Binários de release não precisam de Go: o script de instalação baixa o arquivo compactado para o seu SO e CPU e verifica o SHA-256. Compilações a partir do código-fonte precisam de Go 1.26.2+.

Clone o repositório público, rode o instalador para um arquivo compactado de release, depois escolha um provedor e abra um workspace.

  1. Obtenha o código

    Clone o repositório; o instalador e o código-fonte ficam lá.

  2. Instale o binário

    O script baixa e verifica o arquivo compactado para o seu SO e CPU e instala ovc em ~/.local/bin (ou %LOCALAPPDATA%\Programs\OpenVibeCoding no Windows). Adicione esse diretório ao PATH se ovc não for encontrado. No Windows, reabra o PowerShell depois que o instalador atualizar o PATH.

  3. Escolha um modelo

    ovc --setup oferece servidores locais e presets de planos gratuitos e então testa uma requisição real.

  4. Abra um projeto

    Aponte o ovc para um workspace. Leituras são imediatas; escritas e comandos esperam aprovação.

git clone https://github.com/iagoluch/OpenVibeCoding.git
cd OpenVibeCoding
bash scripts/install.sh
# if ovc is not found, add ~/.local/bin to PATH
ovc --setup
ovc --workspace /path/to/project
git clone https://github.com/iagoluch/OpenVibeCoding.git
cd OpenVibeCoding
./scripts/install.ps1 -AddToPath
# reopen PowerShell after the PATH update
ovc --setup
ovc --workspace C:\path\to\project

Status

O OpenVibeCoding está em desenvolvimento ativo. O comportamento nativo do runtime em macOS e Windows ainda requer validação nessas máquinas; os fluxos de navegador, desktop e sandbox no Linux foram testados. Compilação cruzada não certifica o comportamento nativo do runtime. Veja a última release ou o guia completo.
